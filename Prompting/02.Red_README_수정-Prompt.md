## 반영할 TDD × Cursor AI 워크플로우 (슬라이드 3.9 내용, 이미지 없이 텍스트로 포함)
교육 슬라이드 제목: RBAC × TDD × Cursor AI — 실전 워크플로우. 본 저장소는 RBAC가 아니라 단위 변환(BCE)이지만 동일한 5단계 TDD 흐름을 README에 그대로 적용한다.

C2C Traceability 흐름: 개념(Concept) → 실패 테스트(Failing Test) → 최소 구현(Minimum Implementation) → 리팩터(Refactoring) → Git 커밋으로 추적.

5단계 매핑 (RBAC 예시 → UnitConverter):
- ① 개념 정의(RED 준비): RBAC는 Role·Permission Entity(ECB). 여기서는 LengthQuantity, MetersPerUnit, UnitCatalog, ConversionEngine(BCE Domain Entity). Cursor 예: PRD §4.2 BCE에 맞게 Domain Entity 책임·불변식·meter 허브 환산식만 정의하고 구현은 최소 헤더 스켈레톤만.
- ② 실패 테스트 작성(RED): RBAC는 viewer 삭제 403, 메뉴 visibility pytest RED. 여기서는 Catch2로 환산 불변식·POL-NEG·파싱 계약 테스트를 먼저 작성하고 ctest에서 의도적으로 FAIL 확인. Cursor 예: PRD §5.1·§4.3에 맞는 Catch2 Domain 테스트를 먼저 작성. meter:2.5 → feet≈8.2(1dp), yard≈2.7(1dp), 음수 value create 실패, feet↔yard meter 경유 일치. 구현 없이 테스트만 추가.
- ③ 최소 구현(GREEN): RBAC는 is_visible() 최소 통과. 여기서는 RED 테스트만 통과하는 최소 Domain/Boundary 코드.
- ④ 리팩터(REFACTOR): RBAC는 JWT·DB 권한. 여기서는 Catalog 단일 출처, Formatter 분리, config/units.json 로드.
- ⑤ Git 커밋·추적: RBAC 예 feat: RBAC menu visibility control. 여기서 예 test: add GH-6 negative value boundary RED, feat: domain conversion engine GREEN. C2C로 PRD invariant → TC ID → 커밋 메시지 연결.

README에 현재 단계는 ①~② RED만 강조하고 ③~⑤는 다음 단계로 짧게 요약.

RED 단계 Catch2 예시(README 코드 블록용, pytest 대신 Catch2):
TEST_CASE meter 2.5 converts to feet 8.2 at 1dp [domain][red] — bootstrap_default_three_units, ConversionEngine::convert meter 2.5, feet WithinAbs 8.2 0.05
TEST_CASE meter:-2.5 rejected before conversion [boundary][red] — run_cli meter:-2.5, exit 1, stderr Value must be positive: -2.5
RED 단계에서는 스텁·실패가 정상임을 명시.

용어 박스(README 한 블록): BCE=Boundary·Control·Domain·Data 분리, C2C Traceability=PRD invariant→Catch2 TC→커밋 연결, RED=계약을 테스트로 먼저 고정·구현 전 의도적 실패, POL-NEG=음수·0 거부, POL-OUT=원입력·table 1dp half-up.
