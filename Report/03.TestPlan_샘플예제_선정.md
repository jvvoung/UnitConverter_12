## 1. Executive Summary

본 세션에서는 **비즈니스 로직 문구(`1 meter = 3.28084 feet`, `1 meter = 1.09361 yard`)의 문서·코드 위치**를 전수 조사하고, README·PRD를 근거로 **테스트 플랜 작성용 샘플 예제 1건**을 선정하였다.

| 구분 | 결과 |
|------|------|
| 관계식 문구가 있는 문서 | `docs/requirements.md`, `docs/PRD.md`, `README.md` (3곳) |
| 관계식 수치가 쓰인 코드 | `UnitConverter.cpp` (레거시 단일 파일) |
| 테스트 플랜 대표 예제 | **`meter:2.5` CONVERT · table 출력** (AC-02·기본 요구사항 1·4) |
| 구현·Catch2 | 변경 없음 (M1 RED·GREEN 미착수 유지) |

**핵심 결론**: Golden 입력 `meter:2.5`는 문서 정본·인수 기준·비즈니스 로직 검증·정상/경계 케이스 확장을 **한 기능 단위**로 묶기에 가장 적합한 테스트 플랜 앵커이다.

## 3. 비즈니스 로직 문서·코드 추적

### 3.1 관계식 문구 (`1 meter = 3.28084 feet` / `1 meter = 1.09361 yard`)

| 위치 | 행·절 | 표현 |
|------|--------|------|
| [docs/requirements.md](../docs/requirements.md) | §비즈니스 로직 (37–38) | 불릿 2건, **문구 일치** |
| [docs/PRD.md](../docs/PRD.md) | §3.3 Background (125–126) | 규칙 1·2, **문구 일치** |
| [docs/PRD.md](../docs/PRD.md) | §5.1 표 (211–212) | `1 m = 3.28084 ft`, `1 m = 1.09361 yd` |
| [docs/PRD.md](../docs/PRD.md) | §5.1 검증 (214) | `k_feet = 1/3.28084`, `k_yard = 1/1.09361` |
| [README.md](../README.md) | 지원 단위 표 (230–231) | 관계식 열, **문구 일치** |

**정본 우선순위** (README 명시): 충돌 시 **[PRD](../docs/PRD.md) > requirements.md**. requirements의 관계식은 PRD Background·§5.1과 정합한다.

### 3.2 `meters_per_unit` (k) 상수

| unit | k | 유도 관계 |
|------|---|-----------|
| meter | `1.0` | 기준 |
| feet | `0.3048` | `1/3.28084` |
| yard | `0.9144` | `1/1.09361` |

**환산식** (PRD·README 공통): `target_value = source_value × (k_source / k_target)`. feet↔yard **직접 쌍 하드코딩 금지** (PRD NG-03).

## 4. 테스트 플랜 샘플 예제 선정

### 4.1 선정 기준 (요청 정의)

| # | 기준 | 설명 |
|---|------|------|
| 1 | README 기본 요구사항의 **핵심 변환** | CONVERT·전 단위 출력 |
| 2 | 비즈니스 로직 **직접 검증** | `3.28084` / `1.09361` 관계가 결과에 반영 |
| 3 | **정상 + 경계** 확장 가능 | 동일 기능에 양수 정상·음수·0 거부 묶음 |

### 4.2 선정 결과 (1건)

| 항목 | 내용 |
|------|------|
| **기능 이름** | meter 기준 CONVERT — table 출력 (meter → feet/yard 환산) |
| **requirements 근거** | **기본 요구사항 1번** (대표 입출력), **기본 요구사항 4번** (변환 정확도 TC) |
| **PRD·README 근거** | **AC-02** (§7.1), Golden `meter:2.5`, §3.3 규칙 1·2, §6.2 table |
| **입력 예시** | `meter:2.5` |
| **기대 출력 (table, 1dp half-up)** | 아래 2줄, exit `0`, stderr 빈 |

```text
2.5 meter = 8.2 feet
2.5 meter = 2.7 yard
```

| **수치 근거** | `2.5 × 3.28084 = 8.2021` → half-up **8.2**; `2.5 × 1.09361 = 2.734025` → **2.7** |
| **Domain 허용오차** (PRD §4.3) | `|a−e| ≤ max(1e−9, |e|×1e−9)` (raw: feet ≈ 8.2021, yard ≈ 2.7340) |

### 4.3 선정 이유 (요약 2줄)

1. README·PRD·requirements의 **공통 Golden 입력**이며, `8.2` / `2.7`이 Background 규칙 1·2(meter 허브·`3.28084`·`1.09361`)와 **직접 대응**한다.
2. 동일 CONVERT 흐름에 **AC-02 정상 경로**와 **POL-NEG**(`meter:-2.5`, `meter:0` 등)를 한 테스트 플랜에 연속 배치할 수 있다.

### 4.4 동일 기능 확장 시나리오 (테스트 플랜 초안용)

| 구분 | 입력 | 기대 (요약) | 근거 |
|------|------|-------------|------|
| Happy path | `meter:2.5` | §4.2 stdout, exit 0 | AC-02, requirements §1 |
| POL-NEG | `meter:-2.5` | exit 1, `Value must be positive: -2.5` | PRD §3.3, README 대표 실패 3건 |
| POL-NEG | `meter:0` | 0 거부 (동일 정책) | PRD POL-NEG-01~03 |
| Domain | `meter:2.5` | feet WithinAbs(8.2, 0.05) 등 | README Catch2 RED 스니펫 |
| Boundary E2E | `meter:-2.5` | Domain 호출 전 거부 | README `TEST_CASE` Boundary 예시 |

### 4.5 검토했으나 본 보고서에서 대표로 채택하지 않은 예제

| 예제 | 미채택 사유 (요약) |
|------|-------------------|
| `feet:8.2` 단독 | AC-03·POL-OUT 검증에 유리하나, **3.28084 관계식 직독**보다 역산·prefix 정책 비중이 큼 |
| `meter:5.0` | README Quick Start용이나 **Golden·AC-02·Catch2 RED** 고정 예가 아님 |
| REGISTER `cubit` | M3·AC-04 영역, **기본 3단위 핵심 변환** 범위 밖 |
| feet↔yard 직접 | PRD NG-03 위반 설계 후보로 **플랜 앵커 부적합** |

## 5. 문서 ↔ 레거시 구현 갭 (선정 예제 기준)

`meter:2.5` 입력 시 [UnitConverter.cpp](../UnitConverter.cpp) 동작과 PRD 계약 비교:

| 항목 | PRD·README (목표) | UnitConverter.cpp (현재) |
|------|-------------------|---------------------------|
| table 1dp | `8.2 feet`, `2.7 yard` | **전체 정밀도** 출력 (예: `8.2021 feet`) |
| POL-NEG | `value ≤ 0` 거부 | **음수·0 검증 없음** (`stod`만) |
| stderr 메시지 | `Value must be positive: {value}` | 미구현 |
| meter 허브 k | Catalog `0.3048` / `0.9144` | `3.28084` / `1.09361` 직접 사용 (수치는 동치) |
| 아키텍처 | BCE·ConversionEngine | 단일 `main` 분기 |

→ 테스트 플랜·RED TC는 **PRD·README 계약**을 기준으로 작성하고, 레거시 실행 결과와의 diff는 **의도적 FAIL**로 관리한다 ([02.Red_README_수정.md](./02.Red_README_수정.md) §6 갭 표와 동일 방향).

## 9. 결론

비즈니스 로직 문구는 **requirements · PRD · README** 세 문서에 일관되게 존재하며, 레거시 **UnitConverter.cpp**는 동일 수치를 분기 상수로만 반영한다. 테스트 플랜의 **단일 앵커 예제**로 `meter:2.5` CONVERT(table)를 선정하였고, 이는 기본 요구사항 1·4, AC-02, Background 규칙 1·2, POL-NEG 확장을 한 흐름으로 연결한다.

다음 실무 단계는 본 보고서 §4.4 시나리오를 **Catch2 RED 테스트 파일**로 이식하고, PRD table 1dp 계약 기준으로 **의도적 FAIL**을 확인하는 것이다.
