## 1. Executive Summary

[RPT-09](./09.DualTrack_RED_테스트작성.md)에서 작성한 Dual-Track RED 테스트를 **순수 RED 스켈레톤** 형태로 정리하였다. 각 `TEST_CASE`는 **이름·태그만** 정의하고 본문은 `FAIL("RED");` 한 줄만 포함한다. 계약 API(`ConversionApplicationService`, `UnitConverterLogic`)는 **헤더 선언만** 유지하며 테스트 파일에서는 **미참조**한다.

| 구분 | RPT-09 보고 시점 | 본 작업 후 |
|------|-----------------|------------|
| RED TC 본문 | `REQUIRE` / `REQUIRE_THROWS_AS` 등 전체 assertion | **`FAIL("RED")` 단일 라인** |
| RED 검증 방식 | **LNK2019** 링크 실패 (미구현 심볼 8건) | **런타임 FAIL** 13/13 (빌드 성공) |
| ctest 전체 | 35/36 passed (RED 타깅 NOT_BUILT) | **35/48 passed** (BCE 35 GREEN + RED 13 FAIL) |
| 계약 헤더 | `red_ui_contract.hpp`, `red_logic_contract.hpp` | **동일** (선언만, GREEN 대기) |
| BCE 기존 TC | 35/35 Passed | ✅ **35/35 유지** |
| 레거시 CLI Open | DEF-002, DEF-003 | **동일** (미수정) |

**핵심 결론**: README Track A/B To-Do에 대응하는 **실행 가능한 RED 스켈레톤**이 저장소에 확정되었다. GREEN 단계에서는 `FAIL("RED")`를 계약 API 호출 + assertion으로 교체하면 된다.

## 13. 결론

Dual-Track TDD RED 단계로 **Track A 6건·Track B 7건** Catch2 **스켈레톤**이 확정되었다. 각 TC는 `FAIL("RED")`로 **실행 시 실패**를 보장하며, 빌드·ctest 파이프라인에서 RED 타깅을 **실행 가능한 상태**로 유지한다. 계약 헤더 2건·CMake 타깅은 RPT-09 산출을 그대로 사용한다. 기존 BCE **35/35 GREEN**은 유지된다.

다음 단계는 §12 순서대로 `UnitConverterLogic` → `ConversionApplicationService` 최소 GREEN 구현, `FAIL("RED")`를 assertion으로 교체, 이후 M2 CLI E2E로 DEF-002·DEF-003을 Closed 처리하는 것이다.
